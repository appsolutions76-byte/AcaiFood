## 1. PIN de retirada e entrega (Crítico, regressão)

A migration `20261003200500_create_check_pickup_and_delivery_pins.sql` (03/10) substituiu as funções seguras do R13. Teste local com o código dela:

| Teste | Resultado |
|---|---|
| Usuário **sem login** (`anon`) chama `check_pickup_pin` com `4821` | ✅ aceito → pedido vai a `DELIVERING` |
| Sem login, `check_delivery_pin` com `0000` num pedido **sem PIN gravado** | ✅ aceito → **`RECEIVED`** (libera repasse/saque) |
| Sem login, PIN errado num pedido com PIN | conta tentativa (5 erros = `PIN_LOCKED`) |
| Outro motorista logado | recusado (ok) |

Causas:
- **PIN mestre:** `v_valid := (v_real = v_pin OR v_pin = '4821' OR v_pin = '9354')`. As telas da batedeira e do fornecedor mostram `4821`/`9354` quando não há PIN, e `get_my_order_pins_bulk` devolve `'4821'` como padrão.
- **Sem PIN → aceita qualquer um:** nos dois `check_*_pin`, `ELSE v_valid := TRUE` e o PIN digitado é gravado como o "certo".
- **Anônimo passa:** `IF v_order.driver_id IS NULL OR v_order.driver_id <> v_caller_id`. Com `v_caller_id` nulo, a comparação dá `NULL` e o `IF` não bloqueia. Além disso, a migration dá `GRANT EXECUTE … TO anon`, e a chave anon é pública (vai no app).
- **Trigger esvaziado:** `validate_delivery_pin_trigger` agora só limpa `provided_pin`. A regra "`RECEIVED` só pela função segura" saiu. Hoje o `REVOKE UPDATE` em `orders` segura, mas a segunda barreira foi perdida.
- **Leitura direta de volta:** `check_delivery_pin` lê de novo `orders.delivery_pin`.

→ **Corrigir já** (migration nova; não editar a antiga):
- tirar `4821`/`9354` e o "aceita se não houver PIN";
- trocar a checagem por `IF v_caller_id IS NULL OR v_order.driver_id IS DISTINCT FROM v_caller_id`;
- `REVOKE EXECUTE … FROM anon`;
- restaurar o trigger do R13 (`acaifood.pin_verified_order`);
- PIN ausente = erro "PIN não gerado, contate o suporte" (o admin regenera);
- telas sem PIN fixo;
- conferir em `pin_attempt_log` se houve confirmações com `4821`/`9354` ou de pedidos sem PIN desde 03/10.

Se o erro de `crypt()` foi o motivo da troca, a correção certa é `SET search_path = public, extensions` na função do R13, sem afrouxar a regra.

## 2. Saques e transferências (Crítico, regressão)

**2.1 Destino do saque.** `buildAsaasTransferPayload` (04/10) escolhe, nesta ordem:
1. `pix_key`;
2. CPF/CNPJ;
3. **e-mail de login como chave Pix**;
4. só por último a `walletId`.

`processWithdrawalApproval` só recusa se não houver nenhum dos quatro, então `isAccountActive` não bloqueia nada.

Problemas:
- o dinheiro sai da conta principal da Eletromecânica Baia para chaves externas, fora do fluxo de subconta do contrato;
- o e-mail pode ser chave Pix de **outra pessoa**.

→ Saque **só** para `asaas_wallet_id` com `asaas_account_status = 'APPROVED'`; sem isso, `FALHOU` com mensagem clara. Remover os ramos de chave Pix, CPF e e-mail.

**2.2 `/api/asaas/transfer` reaberta.** No R12 ela devolvia 410. Agora o admin envia qualquer valor para qualquer chave Pix ou walletId, sem `admin_audit_log`. Com o MFA opcional (seção 4), uma sessão de admin roubada basta.
→ Voltar ao 410, ou exigir `withdrawal_request`/`settlement` existente, valor recalculado no servidor, walletId aprovado e log.

**2.3 Idempotência que não funciona.** A trava `PROCESSING` está certa, mas a consulta "já existe transferência?" usa `requestRow.transfer_attempt_id`, que **já é o `attemptId` novo** (o `requestRow` é a linha devolvida pela própria trava). Ela nunca acha a tentativa anterior.

Cenário:
1. O Asaas cria a transferência, mas a resposta se perde (timeout).
2. O saque fica `FALHOU`.
3. O reprocessamento cria uma segunda transferência.

→ Ler o `transfer_attempt_id` **antes** da trava e consultar por ele. Também tratar timeout/erro de rede como `PROCESSING` (a confirmar), não como `FALHOU`.

## 3. Banco e privacidade

**3.1 🗄️ Lista de pedidos (Crítico se `20261002060000` rodou).**
- O `GRANT SELECT (…)` não inclui `seller_amount`, `driver_amount` nem `total_delivery_fee`.
- `ORDER_SELECT_FIELDS` e `ORDER_SELECT_FIELDS_LEGACY` pedem essas três colunas, e `partnerBalance.ts` mostra que elas existem.
- Resultado: as duas consultas falham com "permission denied" e cliente, loja e motoboy veem a lista vazia.

→ Teste: abrir o app como cliente com um pedido. Se a lista vier vazia, tirar as três colunas das duas consultas (usar `seller_payout_amount`/`driver_payout_amount`/`delivery_fee_amount`) ou incluí-las no GRANT.

**3.2 🗄️ Chave de API das subcontas (Crítico se a policy de `users` libera leitura).**
- `subaccount/route.ts` grava `accountData.apiKey` em `users.asaas_account_api_key`.
- `fetchLojas` faz `select('*, storefronts(*, products(*))')` em `users` filtrando lojas, e `fetchAllUsers` lê todos.
- Se a policy de SELECT de `users` deixa ver outras linhas (o app precisa disso para mostrar lojas), qualquer usuário — talvez até visitante — recebe as chaves que movimentam as subcontas, além de CPF/CNPJ, chave Pix, renda e data de nascimento.

→ Teste no SQL Editor:

```sql
select grantee, privilege_type from information_schema.column_privileges
where table_name='users' and column_name='asaas_account_api_key';
```

E no navegador: DevTools → Network → requisição `users?select=*` → ver se a resposta traz `asaas_account_api_key`.

→ Correção:
- `REVOKE SELECT ON users FROM anon, authenticated` + `GRANT SELECT (colunas públicas)`, ou uma view `public_storefronts`;
- mover a chave para uma tabela só do `service_role` (ou Vault);
- trocar os `select('*')`;
- se a chave vazou, pedir ao Asaas a rotação das chaves das subcontas.

**3.3 Radar.** `approx_lat/lng` com 3 casas decimais (~110 m) praticamente aponta a casa do cliente → usar 2 casas (~1 km) ou só o bairro. O radar já cai no bairro do cadastro do comprador quando `delivery_bairro` é nulo; tudo bem.

**3.4 "Fallbacks" que gravam direto em `orders`.**
- `validar_pin`, `validar_pin_retirada` e `aceitar_motorista` tentam `update` direto em `orders` (`RECEIVED`, `DELIVERING`, `driver_id`) quando a RPC falha.
- Hoje o `REVOKE UPDATE` bloqueia, mas é código que confirma entrega sem PIN se um GRANT voltar.
→ Remover os fallbacks; erro da RPC = mensagem ao usuário.

**3.5 Função `asaas-create-subaccount`.** O cadastro chama `supabase.functions.invoke('asaas-create-subaccount')` antes da rota da API, mas a pasta `supabase/functions` está vazia. 🗄️ Se a função existir no painel do Supabase, ela cria subconta **sem KYC nem aceites** → apagar a função e a chamada.

## 5. Contrato Asaas

- **Cadastro de parceiro (ordem errada):**
  - Para parceiro fundador (gratuito), `registerUser` tenta criar a subconta **antes** de o cadastro registrar os aceites → `/api/asaas/subaccount` devolve 400 ("aceites pendentes").
  - Logo depois, a tela chama `/api/asaas/activation` **sem `Authorization`** → 401, e o Pix da taxa não aparece.
  - A subconta só sai no login seguinte (pelo `hasKycData`).

  → Registrar os aceites antes de criar a subconta e enviar o token nas duas chamadas.
- **Aceites:**
  - o envio a `/api/terms/accept` ignora erro;
  - não há aceite no próximo login para usuários antigos;

- **`PartnerActivationGuard`:** não pede data de nascimento, renda nem tipo de empresa. Parceiro antigo sem esses dados nunca consegue criar subconta.
- **Taxa de ativação (2.3):**

  - `founderQuota.ts` e `subaccount` leem primeiro a coluna `activation_fee_enabled` (`NOT NULL DEFAULT true`);
  - resultado: desligar a taxa no admin **não tem efeito**, e não há log.

  → A tela grava em `activation_fee_enabled`, com `admin_audit_log`. Parar de usar `asaas_platform_wallet_id` como depósito de JSON (o suporte também grava lá).
- **Relatório mensal (2.5):**
