## A — Críticos

**C1. Qualquer usuário cadastrado vira admin nas rotas de API (novo).**
`lib/apiAuth.ts`, linha ~86: aceita como admin quem tiver `user.user_metadata.role === 'admin'`. No Supabase, o `user_metadata` é **editável pelo próprio usuário** (`supabase.auth.updateUser({ data: { role: 'admin' } })`, com a anon key pública). Qualquer pessoa que crie uma conta passa nas rotas `authorizeRequest(['admin'])`:
- `/api/admin/clear-data` → **apaga todos os pedidos de produção**;
- `/api/admin/delete-user`, `/api/admin/reset-balances`;
- `/api/admin/reconcile-payment` (`confirm_manual`) → marca qualquer pedido como pago sem pagar;
- `/api/asaas/transfer` com `orderId` → manda o repasse de um pedido entregue para **uma chave Pix escolhida pelo atacante**;
- `/api/asaas/sweep?force=true`, aprovação de saques, anúncios, configurações.
→ Remover a linha do `user_metadata`. Admin só por `users.role`/`users.is_admin` (o trigger do banco já impede autopromoção nessas colunas).

**C2. Estorno e cancelamento de qualquer pedido sem login (novo).**
`/api/asaas/refund` chama `authorizeRequest`, mas **nunca confere o resultado** e não verifica se quem chama é o comprador, o vendedor ou o admin. Aceita até prefixo do id (`PED-a`, `PED-b`…), que casa com os 50 pedidos mais recentes. Qualquer pessoa, sem conta, estorna via Pix ou cancela todos os pedidos pagos que ainda não foram entregues.
→ `if (!auth.authorized) return 401`; só o comprador (antes do preparo), o vendedor do pedido ou o admin; só UUID completo.

**C3. Pedido de R$ 300 pago com R$ 1 (A5 continua aberto por outra porta).**
A Edge Function `asaas-checkout` continua publicada pelo CI, aceita `value` e `split` do corpo com a anon key e **troca o `asaas_payment_id` do pedido** pela cobrança nova. Depois, `GET /api/asaas/status?orderId=…` (sem login) procura no Asaas qualquer cobrança paga com aquele `externalReference` e marca o pedido como `PAID`, **sem comparar o valor**.
→ Apagar a Edge Function `asaas-checkout` (e removê-la da pasta para o CI não republicar). No `GET /status`, só aceitar a cobrança cujo id é o `asaas_payment_id` gravado e cujo valor é igual a `charged_amount`.

**C4. Motoboy ou loja marca o pedido como entregue sem PIN e saca (novo, combinação de A6 + A2).**
O saldo de saque conta pedidos `DELIVERED` e `COMPLETED`. O trigger de PIN só barra a mudança para `RECEIVED`. Pela RLS de `orders` (inalterada desde 27/08), qualquer usuário logado pode dar UPDATE em pedido `PAID/PREPARING/READY` sem motorista: basta gravar `driver_id = eu` e `status = 'DELIVERED'` para o frete entrar no saldo. A loja pode fazer o mesmo nos próprios pedidos e, com status `COMPLETED`, o cliente perde o estorno automático.
→ Saldo conta **só** `RECEIVED` (o único status que passa pelo PIN). Revogar UPDATE de `status`, `driver_id` e `payout_*` para `authenticated`; status só por RPC/servidor (A6/A7).

**C5. Pagamento em dobro (A1 continua aberto).**
O checkout ainda manda a parte do vendedor via split, e a regra ficou mais frouxa: basta ter **qualquer** `asaas_wallet_id` que não esteja `REJECTED`. O saldo de saque não exclui esses pedidos, então o vendedor recebe no split e de novo no saque.
→ Implementar a decisão de 23/09: tirar o split do checkout e liquidar depois do PIN.

**C6. Saque para chave Pix digitada (A4 continua aberto).**
`isAccountActive` aceita qualquer `pix_key` ou `cpf_cnpj`, que o próprio usuário pode alterar direto no banco (GRANT UPDATE). A chave digitada tem prioridade sobre a wallet. Quem invadir a conta de um parceiro troca a chave e saca.
→ Pagar só para a wallet da subconta aprovada (decisão de 23/09).

**C7. `link-wallet` aprova qualquer UUID (B6 piorou).**
`isApproved` começa `true` e só vira `false` se o Asaas responder OK com outro status. O endpoint consultado (`/accounts/{walletId}`) espera o id da conta, não o walletId. Com 404, qualquer UUID vira `APPROVED` + `split_enabled = true`, e o checkout passa a mandar dinheiro para essa wallet.
→ Só o servidor grava a wallet, a partir da subconta criada pela plataforma; status vindo só do webhook de conta do Asaas.

**C8. Preço e distância definidos pelo celular (A10 continua aberto).**
`productsSubtotal`, preço dos itens e `deliveryDistanceKm` vêm do app. Alterando a requisição, o cliente paga R$ 0,01 pelos produtos ou zera o frete.
→ Recalcular o subtotal a partir de `products` e a distância a partir das coordenadas da loja e do endereço.

## B — Altos

**H1. Saque pago em dobro enquanto está `PROCESSING`.** O pedido de saque só bloqueia se já existir um `PENDENTE`/`APROVADO`. Durante `PROCESSING` (transferência enviada, esperando o webhook), os pedidos ainda não estão marcados como pagos: o parceiro pede de novo com os mesmos pedidos e, se o admin ou o automático aprovar, paga duas vezes. O mesmo vale para um saque `FALHOU`: pode ser reaprovado **e** um saque novo pode incluir os mesmos pedidos.
→ Bloquear novo saque com `PROCESSING`/`FALHOU` aberto; marcar os pedidos como "reservados" ao criar o saque.

**H2. Saque sem idempotência (B5).** Se a rede cair depois do Asaas aceitar a transferência, o saque vira `FALHOU` e pode ser reaprovado. → Enviar `externalReference` = id do saque e consultar antes de reenviar.

**H3. Webhook devolve erro 400 e pode parar a fila do Asaas (novo).** Quando o valor diverge, a rota responde 400. O Asaas reenvia e, após falhas seguidas, **pausa a fila de webhooks**: nenhum pagamento é confirmado até alguém reativar no painel. Com C3, um atacante provoca isso de propósito. → Registrar o incidente e responder 200.

**H4. Webhook faz o pedido voltar para `PAID`.** Qualquer evento repetido ou posterior com status `RECEIVED` grava `PAID` e um novo `paid_at` por cima de `PREPARING`/`DELIVERING`, e gera um PIN novo, zerando as tentativas. O `PixModal` faz o mesmo no app (C2 da 6ª auditoria, aberto). → Só atualizar `WHERE status IN ('PENDING','AWAITING_PAYMENT')`.

**H5. Saldo calculado com taxa diferente da cobrada (B3 parcial).** O checkout agora usa a cidade do comprador, mas `partnerBalance` e `/api/asaas/transfer` procuram colunas de cidade que não existem em `orders` e usam a taxa global de **hoje**. → Gravar no pedido, no checkout, os valores de repasse (snapshot) e pagar por eles.

**H6. Saque automático não processa nada (provável) 🗄️.** O `sweep` busca `partner:partner_id(city)`, mas a coluna em `users` é `cidade`. Se `city` não existir, a consulta falha e a rota responde "nenhuma solicitação pendente". O cron roda uma vez por dia, às 19h de Belém, e grava "já rodou hoje" mesmo quando pulou cidades com horário mais tarde. ⚙️ Conferir nos logs da Vercel se o cron chega autenticado.

**H7. Admin e PIN.** PIN de entrega e retirada continuam em texto puro, visíveis no radar para qualquer motorista logado, e `check_delivery_pin`/`check_pickup_pin` não conferem quem chama (A9, aberto).

## C — Médios

**M1. Textos enganosos (C3, aberto).** As telas de motoboy, fornecedor e batedeira ainda dizem "transferir instantaneamente via PIX" e "2 saques por dia" (contador no navegador). O saque depende de aprovação.
**M2. Coleta (C1, aberto).** Na coleta, a loja de destino é o próprio comprador (`storeTargetId = validBuyerId`).
**M3. Pedido local `PED-###`.** O store ainda cria pedidos locais com id `PED-` antes do checkout. Confirmar que não sobrou nenhum caminho que mostre Pix para pedido inexistente.
**M4. Conciliação manual.** O mesmo E2E pode conciliar vários pedidos (falta checar se já foi usado). O pedido conciliado entra no saldo de saque automático, mas o dinheiro está **fora** do Asaas: o repasse sai do saldo de outros clientes.
**M5. Banco sem versionamento completo (C6) e Edge Functions mortas (C7).** `asaas-checkout`, `asaas-status`, `asaas-webhook`, `payout-sweep`, `remove-account`, `clear-orders` continuam sendo publicadas a cada push.
**M6. Arquivos gigantes e zero testes (C8/C9).** `admin/page.tsx` 268 KB, `batedeira/page.tsx` 175 KB, `useAppStore.ts` 154 KB.
